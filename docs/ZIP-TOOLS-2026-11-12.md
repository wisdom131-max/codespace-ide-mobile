# ZIP Tools — 2026-11-12

Baseline: `03a69a6` (MCP lifecycle, CI 43135229948 GREEN), docs `7635923`. Scope: three tools —
`zip_create`, `zip_extract`, `zip_list` — on top of the archive engine the app already ships.

## 1. Audit

What already existed, and where:

| Capability | Where it lives | Reused? |
|---|---|---|
| Archive engine | `java.util.zip` (`ZipFile`, `ZipInputStream`, `ZipOutputStream`) — already a JDK dependency | YES, unchanged |
| Zip creation | `util/WorkspaceManager.createSnapshot` — `ZipOutputStream`, 64 KB streamed copy, excludes `.ide-trash/` and `.autosave/` | YES, same pattern |
| Archive reading + per-entry extract | `ui/panes/ArchiveViewer.kt` — `ZipFile`, `readTextStreaming`, 64 KB copy | YES, same pattern |
| Tar/backup archive | `terminal/BackupTar.kt` (separate format, not ZIP) | not applicable |
| Path containment | `resolver/PathResolver` + `ToolPathResolver` for host paths | YES for tool-level resolution |
| Safe writes | `util/AtomicJson` (write-temp-then-rename) | YES, same shape for the archive itself |

Gaps found: no reusable ZIP *extraction* engine. Extraction logic existed only inside the archive
viewer, bound to Compose state and with no ZIP-Slip guard, no entry/size limits, and no resource
accounting. Nothing in the codebase could be called from a tool.

**Reuse decision:** keep `java.util.zip` as the single engine (option 1/3 of the preference order).
No new dependency, no second archive implementation. The missing piece is a *policy* layer, not an
engine, so `util/ZipEngine.kt` was written against the JDK API using the copy/stream patterns that
`WorkspaceManager` and `ArchiveViewer` already established.

Rejected alternatives: a bundled `unzip` binary (the proot image may or may not carry one, its exit
codes and output differ by build, and shelling out to it would bypass the in-process path checks);
Apache Commons Compress (a new dependency for capability the JDK already has).

## 2. Implementation

- `util/ZipEngine.kt` (new, 483 lines) — the whole archive policy: create, extract, list, path
  validation, limits, streaming. Pure `java.io`, so it is unit-tested without an emulator.
- `agent/ZipTools.kt` (new) — the tool layer: resolves paths against the open project, formats a
  bounded human-readable result, turns engine outcomes into the existing tool-result strings.
- `chat/panel/ToolRegistry.kt` — three `ToolSpec`s with JSON schemas.
- `chat/panel/ToolMeta.kt` — categories FILES, discovery keywords (`zip`, `archive`, `compress`,
  `unzip`, `extract`, `tarball`), `destructive` on create/extract so they keep asking.
- `agent/AgentTools.kt` — three executor branches plus the `BUILTIN_TOOL_NAMES` entries (registry
  parity is the executable list, so a spec without a branch fails a test).

Modes: `zip_list` is read-only and exposed in Ask/Edit/Agent; `zip_create` and `zip_extract` write,
so they are Edit/Agent only.

## 3. Security

- **ZIP Slip.** Every entry name is checked for absolute paths, UNC paths, Windows drive letters and
  any `..` segment, then the resolved target is canonicalised and required to stay inside the
  extraction root. A name that fails any check is SKIPPED and reported, never written.
- **Symlinks.** No entry can create a symlink (extraction always writes regular files). Before each
  write, every ancestor directory is checked for being a symlink, and the canonical target check
  catches a link that would redirect the write outside — both are reported as skips.
- **Overwrite.** Off by default; an existing file is skipped and the result is marked *partially
  extracted*. `overwrite = true` is explicit per call, and the check runs on the canonical target so
  path normalisation cannot bypass it.
- **Limits** (chosen for a phone, documented in the file): 2,000 entries, 256 MB total uncompressed,
  128 MB per entry, ratio above 200:1 treated as suspicious once an entry exceeds 8 MB, listing
  output capped at 200 entries per call plus a `offset` hint. Hit any limit → stop, report partial.
- **Streaming.** 64 KB buffer copies; no archive is ever read into memory, and `ZipFile` gives
  random access for listing without inflating anything.
- **Output.** All three tools return bounded text (a handful of lines plus capped lists), so a large
  archive cannot flood the prompt.
- **Permission enforcement.** Untouched. The tools are ordinary builtin tools: they respect the
  existing mode gate, the approval flow and the AUTP/approval levels. They were NOT added to any
  safe/auto-approved list, and nothing about MCP approval changed.

## 5. Known limitations

- Only DEFLATE and STORED are supported (the JDK's set); an entry using another method is reported
  as unsupported rather than guessed at.
- Encrypted ZIP entries are not supported and are reported as failures.
- Extraction is synchronous inside the tool call, bounded by the limits above, so a huge archive
  fails fast instead of running forever. There is no resumable extraction.
- `zip_create` stores entries with relative paths from the resolved source root; `dest_dir` is not a
  tool argument.
- No device testing has been run. Consolidated phone testing remains roadmap item 14.
