# P2.C - RAR and Zstandard archive support

Date: 2026-11-12
Scope: extend the P2.B archive engine to the two formats it used to refuse. **No build, no test run and
no CI has happened for this change** - the whole section below is code plus reasoning, and the honest
status of every claim is the last section.

## 1. What the engine reads now

| Format | Listing | Extraction | Reader |
|---|---|---|---|
| RAR 1.4 | yes | **refused with a reason** | junrar (headers only for this variant) |
| RAR 4.x (RAR15) | yes | yes | junrar |
| RAR 5.x (RAR50) | yes | yes | junrar |
| `.zst` (single stream) | one synthetic entry | yes, to one file | zstd-jni (`@aar`) |
| `.tar.zst` | real entry list | yes, per entry | zstd-jni + commons-compress tar |
| 7z | **real entry list (was empty)** | unchanged (refused: no entry walk) | commons-compress |

Signature detection is unchanged in kind: `ArchiveEngine.kindOf` sniffs bytes, never extensions, so a
renamed `.rar` is still a RAR. `resolvedKind` adds one refinement for Zstandard - a `.zst` may hold a
tar, and only the payload can say so. It decodes 512 bytes to answer that, not the file.

## 2. RAR - `agent/RarEngine.kt`

junrar 8.1.2 is a pure-Java port of the UnRAR sources: no native code per ABI, Java 8 bytecode, one
transitive dependency (`slf4j-api`, silenced with `slf4j-nop`).

Three deliberate decisions:

1. **Extraction goes through a counting sink, not `Junrar.extract`.** `archive.extractFile(header, out)`
   writes into our own `OutputStream`, which throws the moment an entry passes the per-file ceiling. A
   bomb therefore stops mid-write and the partial file is deleted, rather than being measured after it
   has already filled storage. It also keeps every limit in one family with `ZipEngine`'s.
2. **The dictionary is capped at 64 MiB.** RAR5 may declare a dictionary up to 4 GiB and junrar
   allocates the window when it decodes; on a phone that is a guaranteed OOM. `ArchiveOptions
   .maxDictionarySize` is set to 64 MiB, so an archive that genuinely needs more is refused instead of
   killing the process.
3. **`getInputStream(header)` is not used.** It is a piped stream with a background extraction thread
   per entry. `extractFile` is synchronous and keeps the calling thread in control of the bounds.

Refusals, each with a sentence the model can act on: RAR 1.4 extraction, password-protected archives of
any variant, unreadable headers (counted and reported), entries over 128 MiB, archives over 256 MiB
total, more than 2000 entries, and entries expanding past the 200x ratio ceiling.

## 3. Zstandard - `agent/ZstdEngine.kt`

Zstandard is a compressor, not an archive. The engine treats it as such: `.zst` yields exactly one file
named after itself minus the extension, and `.tar.zst` is walked as a tar. A `.zst` never claims an entry
list it does not have.

**The dependency had to change, not just be used.** `zstd-jni:1.5.6-4` was already declared, but as a
**plain jar**, which contains `linux/`, `darwin/` and `win/` natives only - there is no Android path in
it, so the first call on device would throw `UnsatisfiedLinkError`. The `.aar` variant contains
`jni/{arm64-v8a,armeabi-v7a,x86,x86_64}/libzstd-jni-1.5.6-4.so`, which Gradle packages as normal native
libraries. The coordinate is now `com.github.luben:zstd-jni:1.5.6-4@aar`.

Memory is bounded twice: `setLongMax(26)` (64 MiB) refuses a frame that declares a bigger window, and
output is capped by the per-file ceiling on the way out. `setContinuous(true)` keeps a multi-frame
stream (`zstd a; zstd b > out.zst`) decoding to its end instead of stopping at the first frame.

## 5. Security - what did not change

Every boundary from P2.B is reused, not re-implemented: `ZipEngine.unsafeReason` for absolute and
traversal paths, `ZipEngine.safeTarget` for canonical containment, `MAX_ENTRIES` (2000),
`MAX_ENTRY_BYTES` (128 MiB), `MAX_TOTAL_BYTES` (256 MiB), `MAX_RATIO` (200x above an 8 MiB floor),
the explicit overwrite decision, and bounded streaming everywhere.

Added for the new formats:

- **A counting sink** for RAR that aborts an entry mid-write and deletes the partial file.
- **A dictionary ceiling** for RAR (64 MiB) so a declared 4 GiB window cannot be allocated.
- **A window ceiling** for zstd (`setLongMax`) so a frame cannot demand an unbounded decode buffer.
- **A ratio ceiling applied to RAR headers** before extraction rather than after.
- **No link creation of any kind.** junrar exposes no symlink flag, and this is safe because the reader
  only ever writes regular files at canonical-contained paths - it never mints a filesystem object whose
  type comes from the archive.

Not in the register, fixed here: a 7z archive used to list as **"empty (0 entries)"** because the engine
only walked tar streams. `ArchiveEngine.list` now enumerates `SevenZFile.entries`, so the model is no
longer told an archive is empty when it is not. 7z *extraction* is still refused, as before.

## 8. Status of every claim

- **Implemented, not compiled:** `RarEngine`, `ZstdEngine`, the `ArchiveEngine` changes, the Gradle
  coordinates, the `zip_list` description, and the reworked `ArchiveEngineTest` assertion.
- **Documented but not tested:** everything in section 7. Nothing in this document is a claim that the
  code works.
- **Still unsupported:** RAR 1.4 extraction, password-protected RAR, RAR symlink metadata, RAR
  dictionaries over 64 MiB, solid-RAR behaviour (unverified), 7z extraction, and creating either format.
- **Deferred:** an archive-password prompt in the Copilot tool surface; 7z/RAR progress callbacks
  (the engine reports completion, never percentages); the archive browser UI (still P2 backlog).
