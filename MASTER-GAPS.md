## Fix-plan ordering and shared failure pattern

**TOP TIER (co-priority, above every other listed gap): G01, TB01, TB03, SG02, CH01, EX04, EX05, EX07, SG04, TP01, IG02, RG03, RG04, VG01.** The data-integrity chain now reads end to end: **every layer that writes, protects, or recovers user data can fail silently.** An edit can fail to persist with no error (G01, the write), a strip/root close can discard the only live buffer without a dirty warning (TB03, the close warning), crash recovery can delete the only backup while falsely reporting restored edits (TB01, the backup), **the timeline restore — the designated recovery path for exactly this chain — can silently no-op (SG02, the restore)**, and **the chat-apply undo can silently no-op AND misreport (CH01, 2026-09-24 owner ruling: SG02's sibling — same silent-or-misreported recovery failure, different surface; partial batch restore says "Restored 1 file(s)" with no failure mention, total failure says "No checkpoints found to restore" even when checkpoints exist but the copies failed)**. SG02 and CH01 are not separate findings below that chain; they are its LAST links (the recovery surfaces), owner-escalated 2026-09-24. **Plan and verify these together**: a TB03 dialog cannot recover a TB01 backup already deleted, and nothing can restore through an SG02 or CH01 that swallowed the copy failure. **COMPOUND RISK (CH05+CH01, flagged 2026-09-24):** a failed `stage()` falls through to AgentTools.writeFile — an UNGATED direct disk write that creates NO checkpoint and shows NO pending card; the model is told "Wrote N chars", and CH01's undo then reports "No checkpoints found to restore" — the net effect is an edit applied to disk with NO recovery path at all, plus a tool-result success and an undo message that both misstate reality. CH05's fix (refuse on staging failure) and CH01's fix (typed results) must land TOGETHER for this chain to close. EX04 is file-creation/rename path escape, EX05 is archive extraction escape (zip-slip boundary), EX07 is a destructive remove-root scope risk; **SG04 is a credential leak into exfiltration-capable channels (proot argv readable by AI-executed commands; persistent NotificationStore text attachable into AI chat), compromising the user's GitHub account — outside the app's blast radius.** Treat EX04/EX05/EX07/SG04 as one security-relevant tier: containment and credential escape, not mere UI correctness. **TP01 (owner-ruled 2026-09-24) carries its own explicit security flag — REMOTE SERVER COMPROMISE — a distinct class from every app-local finding above: it was the only top-tier gap that lived on a deployed internet-facing server, not on the device. RESOLVED the same day: the live probe confirmed the deployed Render backend accepted a /ws/terminal namespace connect with the dummy ticket `ticket=x` (auth gap live in production; shell blocked only by node-pty's absence, itself not in package.json), the owner chose mitigation option (a) REMOVAL, commit 57236a0 dropped the TerminalModule import, and the post-redeploy probe confirmed the endpoint is GONE — /socket.io/ and /ws/terminal both 404 (socket.io no longer mounted at all; no connection with any ticket is possible), /api/v1/health 200 on the fresh process. Kept in the top tier for the record, marked resolved; re-verify on any future backend deploy that touches dependencies (a re-added node-pty + restored gateway would resurrect the exposure).** **2026-09-24 owner re-ranks:** IG02 (schedule_task structural FlowGate bypass) and RG03/RG04 (cloud-restore tar-entry path traversal + hand-rolled tar name truncation) join the top tier. **VG01 (live-preview server binds all interfaces) was elevated by explicit owner ruling the same day — ranked NOW, not gated on its device check: `ServerSocket(5500)` with no bound address is unconditionally all-interfaces in Java; this needs no empirical confirmation, only documentation. BI06 remains the confirming device check, not the gate. Exposure arguably EXCEEDS the other top-tier findings: no local device access and no malicious file needed — just shared-Wi-Fi proximity, or, via the in-app browser compound path (a malicious page fetched in the app's own browser-mode WebView can read `http://localhost:5500/`), no proximity at all.** RG03/RG04 are the SAME zip-slip family as EX05, on a different archive format (tar from the network vs. zip in Explorer) and a different entry point (cloud restore vs. Explorer extraction). **SHARED-FIX CONFIRMATION: EX05 and RG03/RG04 CAN and should share ONE fix implementation — a single canonical-path containment utility (canonicalize, reject absolute/`..`, require path-separator-boundary containment) consumed by (a) Explorer zip extraction (EX05, `ExplorerPane.kt:1737-1778`), (b) CloudBackupManager tar extraction (RG03/RG04, `CloudBackupManager.kt:271-286`, which should also move to commons-compress), (c) the BackupManager rootfs restore sink (RG07), and (d) New File/Folder/Rename containment (EX04, `ExplorerPane.kt:2146-2334`). One utility, four call sites; the Explorer `startsWith(dirPath)` boundary defect and the raw-`File(destDir, name)` tar defect are the same root cause in two dialects.**

These rankings are for a later user-authorized fix plan, not permission to implement now. Do not use a real project to reproduce them.

**SYSTEMIC GAP S01: unchecked operation outcome and false success.** G01 (file write), EX01 (trash move), EX02 (nested restore) and EX06 (folder create) all permit a success-looking outcome without proving the requested file result. EX02's mechanism is specifically *lost original-path metadata plus the restore UI ignoring the Boolean result*, not an unchecked `mkdirs()` or write call. When planning fixes, prefer a shared typed result/verification contract for file operations and user-facing success notifications, preserving original paths for restore; do not assume one helper alone fixes EX02's metadata loss. Keep the four IDs as traceable manifestations and test them individually, but design the fix as one systemic workstream where feasible. **SR03 extends the same false-success pattern to Search Replace All**: it reports matched-line counts without verifying that the displayed hits were actually replaced. Any shared verification/typed-result contract for S01 must specifically cover SR03 and SR04's write paths too — Search has its own separate Replace All implementations (sidebar and modal) that write disk directly rather than reusing Explorer's file-write logic, so a fix confined to Explorer's helpers would leave them unchecked. SR03 stays below top tier: it misreports but does not destroy data. **IC04 extends the same pattern to IntelliSense auto-import insertion**: the tap-path import apply wraps the whole operation in a swallowed exception, so a failed import insertion disappears without any failure signal — the S01 shared verification design must cover this write path too. **PR01 extends the same pattern to build cancellation**: BuildRunner.currentProcess is never assigned, so cancelBuild() destroys null and sets CANCELLED while the gradle build keeps running, and the completing coroutine then overwrites the status to SUCCESS/FAILED — a person can act on a build status that never happened, a sharper consequence than a miscount. PR01 ranks above PR03 within the Problems group, but the owner directs they be fixed together: PR03's 2000-line output cap swallowing the BUILD SUCCESSFUL/FAILED marker is a second way the same status field ends up wrong — one status-integrity workstream covers both (true process ownership via execOnceWithProcess + marker-preserving output capture + a single authoritative terminal status write).
