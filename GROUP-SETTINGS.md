# Settings: fresh source-only group audit

**State:** app source read; no device test run. `READ A/path:N` is 1-based in `android/app/src/main/java/com/codespace/ide/`, `READ V/path:N` is 1-based in `vscode-src/` (repo root `src/vs/`). This group owns ALL settings surfaces not already owned by another group: the unified JSON settings store (`editor/settings/` — JsonSettingsStore, SettingsSchema, SettingsMigration — initialized at app start, READ A/CodeSpaceApplication.kt:42), the legacy facades that write through it (`ProjectSettingsStore`, `FeatureToggleStore`, `KeyBindingRegistry`), the VS Code-style In-Project Settings dialog (`ui/screens/InProjectSettingsDialog.kt`), the global Settings screen (`ui/screens/SettingsScreen.kt`), the keybindings editor (`ui/panes/KeybindingSettingsPanel.kt`), the theme system (`ui/Theme.kt` + persistence in `ui/CodeSpaceApp.kt` + picker in ProjectShellScreen), and the app lock (`ui/screens/PinLockScreen.kt` + PIN hashing in `data/SecureTokenStore.kt`). **Explicitly claimed by other groups, not re-audited:** the AI provider keys / MK endpoint sections hosted on SettingsScreen (Chat CF01-CF04), MCP servers config in In-Project Settings (Extensions XF18), container backup/restore mechanics (Terminal BackupManager, TP12) and rootfs integrity (Terminal TP04), workspace-restore gating semantics (Recovery, next), and GitHub token storage security (SCM SG04 context). Per COVERAGE-CHECK.md this is the whole settings cluster — nothing in the settings source tree is left unowned after this group. Nothing here is a device outcome or a code-fix authorization.

## Boundary

Chat owns AiKeysSection/MK rows (CF01-CF04); Extensions owns McpServersSection (XF18); Terminal owns BackupManager mechanics (TP12) and rootfs integrity (TP04); SCM owns the token's downstream handling (SG04/SG16); Recovery will own SessionHandoffManager restore semantics that this group's workspaceRestoreEnabled merely gates; Editor owns the save-path divergence consuming `format_on_save` (C-SF01). SK01/SK02 feed the S01 typed-result design pass (they are the settings-boundary instances of it, with importJson already proving the in-codebase model). SK04 is security-relevant but contained: it gates a device-holder threat, not a remote one, and ranks below SG04/EX04-class gaps that cross the process boundary; it should be batched with PinLock hardening whenever app-level security work is scheduled. All SN01-SN36 are predictions; none authorizes code changes.
