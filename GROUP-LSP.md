# LSP: fresh source-only group audit

**State:** app and checked-out VS Code clone read; no device test run. `READ A/path:N` is 1-based in `android/app/src/main/java/com/codespace/ide/`, and `READ V/path:N` is 1-based in `vscode-src/src/vs/`. This group owns the language-server *client* machinery: server configs, install, proot spawn, initialize handshake, JSON-RPC transport, document sync, lifecycle (crash/restart/idle), diagnostics push pipeline, the ~35-method request surface, URI mapping, ctags fallback. Feature *consumers* are boundaries: IntelliSense (IC gaps), Editor E14 squiggles, Problems panel, Search symbol overlays, Explorer rename. ## Reference client comparison (microsoft/vscode-languageserver-node, commit 35409e7)

Added 2026-09-24 at owner request, audit-only, no app change. `READ LSN/...` = `vscode-lsn-src/client/...`. The wire dispatcher itself (request-vs-notification detection and response auto-send) lives in the client's vscode-jsonrpc dependency, not this repo; what the client owns is handler registration and the queue-until-connection machinery below.

| Our gap | Reference client behavior (file + function) | Contrast with ours |
|---|---|---|
| LS01: no response to server-initiated requests | The client registers request handlers immediately after initialize returns: `connection.onRequest(RegistrationRequest.type, ...)` and `connection.onRequest(ApplyWorkspaceEditRequest.type, ...)` inside `handleInitializeResult` (READ LSN/src/common/client.ts:1512-1518), plus `client.onRequest(ConfigurationRequest.type, ...)` in `ConfigurationFeature.register` (READ LSN/src/common/configuration.ts:47-65). `BaseLanguageClient.onRequest` (READ LSN/src/common/client.ts:978-1001) buffers handlers into `_pendingRequestHandlers` while no connection exists (line 995) and flushes them onto the connection at 1508-1515. Responses: `handleApplyWorkspaceEdit` -> `doHandleApplyWorkspaceEdit` serializes conversions through a `workspaceEditLock` Semaphore, runs `validateWorkspaceEdit` (document-version guard), applies via `Workspace.applyEdit`, and returns `{applied}` — the handler's return value IS the JSON-RPC response (READ LSN/src/common/client.ts:2231-2264,2266-2294). `handleRegistrationRequest` (READ LSN/src/common/client.ts:2167) dynamically registers features and resolves. The connection object itself is a ProtocolConnection from `createConnection` (READ LSN/src/common/client.ts:1829-1840), whose jsonrpc layer sends the response and auto-errors unhandled requests. | Our `JsonRpcClient.handleMessage` (READ A/lsp/JsonRpcClient.kt:244-285) has NO branch for a message with both id and method — requests are dropped without even a -32601 error response, and no applyEdit/configuration/registerCapability handlers exist anywhere. Fix shape is visible in the reference: a handler map keyed by method for server requests, flushed responses from handler return values, and a pending-handler buffer for pre-connection registration. |
| LS02: isServerRunning checks only process.isAlive; didOpen lost if sent mid-initialize | Reference state machine: `enum ClientState` Initial/Starting/StartFailed/Running/Stopping/Stopped (READ LSN/src/common/client.ts:479-486), with public state change events fired from the `$state` setter via `getPublicState` (READ LSN/src/common/client.ts:879-899). Crucially `sendRequest` and `sendNotification` reject ONLY in StartFailed/Stopping/Stopped and otherwise `await this.$start()` before sending — so a didOpen arriving during Starting BLOCKS until the connection+initialize completes, then sends; it is neither lost nor rejected (READ LSN/src/common/client.ts:915-926,1021-1048). On top of that, `DidOpenTextDocumentFeature.register` queues `_pendingOpenNotifications` for documents visible before sync registration and flushes them via onOpen listeners and `sendPendingOpenNotifications` (READ LSN/src/common/textSynchronization.ts:112-152,171-185). | Ours checks `process.isAlive` without `initialized` (READ A/lsp/LspManager.kt:858-861), sends didOpen immediately, ignores its false return, and marks `lspOpenedFiles` true anyway (READ A/ui/panes/EditorPane.kt:1460-1461) — the exact failure mode the reference avoids by making senders wait for readiness and by tracking success. Fix shape: gate sends on `isServerInitialized` (or await readiness) and only mark opened when didOpen actually succeeded, plus a pending-open queue. |
| LS03: idle auto-close strands the active editor | The reference client has NO idle/shutdown behavior at all — that is purely our addition for on-device memory. Reference lifecycle: `start()` on extension activation (READ LSN/src/common/client.ts:1293), `stop(timeout=2000)` on deactivation (READ LSN/src/common/client.ts:1584); lifetime is owned by VS Code's activation events, not the client. Closest applicable patterns: crash policy `DefaultErrorHandler.closed()` restarts up to a max count, and 4+ crashes within a 3-minute window trip `DoNotRestart` with a user message — a time-windowed circuit breaker vs our plain 5-count (READ LSN/src/common/client.ts:450-475); and `onDidChangeState` events so the UI can react to state transitions (READ LSN/src/common/client.ts:883-899). | Our idle close is defensible on a 2.8GB device, but the reference's implicit contract is that a client never silently drops service: whoever stops a server owns starting it again. Fix shape: either restart-on-demand from the active editor path (Effect B or a state-change watcher keyed on server state, not tab keys), or reopen on the `onDidChangeState` equivalent of our LspState. |
