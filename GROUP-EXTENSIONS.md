## Recommendation — assistant judgment, NOT a READ citation

This section is judgment for the owner's decision; every READ above stands on its own.

**Smallest real extension mechanism that can sit beside the existing package feature:**

1. **Start with contributions that execute NOTHING.** A `.codespace/extensions/<id>/manifest.json` (id, name, version, activationEvents, contributes) scanned at startup into a registry object. Phase-1 contribution types chosen for zero code execution: commands (registered into the parity-backlog action registry — C-XG09), snippets (SnippetEngine already exists), grammars (the app already ships a tokenization engine), themes/colors later. A manifest-only extension system is genuinely small, safe, and testable, and it makes XG01-XG04 real without any host process.
2. **Then add ONE executable contribution type: a command bound to a gated shell template.** The manifest declares `"contributes": { "commands": [...] }` where a command maps to a command template executed through the EXISTING run paths (terminal chat's gated run_command / FlowGate) — never a new transport. This reuses the permission model instead of inventing an API surface, and gives extensions real capability without an extension host.
3. **Per-extension identity from day one.** Registry entries carry the extension's id; every contribution (command run, snippet insert) is recorded with it. This is the one thing that must not be retrofitted — it is what AgentApiServer lacks (XG02) and what makes later per-extension storage, gating, and uninstalls possible.
4. **Explicitly do NOT build an extension host process** (parity-sweep FINAL-REVIEW §5 already ruled this). The proot guest already is the app's "extension host": untrusted code runs in the rootfs, not the app process. The manifest registry + gated templates gets the VS Code SHAPE (declarative contributions, activation, per-extension identity) at mobile scale.
5. **Coexistence with packages:** keep PackageManagerPane.kt a self-contained section (apt state fully encapsulated: SharedPrefs history + dpkg reads + runPkg); extensions render from the registry in a separate section of the same tab. They must share NOTHING but the container — no shared state, no shared store. The search box can stay apt's; extension search can reuse it behind an interface later.
6. **Removing packages later, cleanly:** because packages own only (a) runPkg+execOnce, (b) the SharedPrefs history, (c) the FEATURED catalog, and (d) the McpPanel card (which is NOT package functionality — it belongs to agent tools and must migrate to Settings/Connectors with P54's pattern when the tab is reshaped), deletion = remove the ExtensionsPanel composable + its four private helpers. McpShellProfile and AgentApiServer are Terminal/Chat-group assets and must not die with the tab. The one seam to protect NOW: keep the SidePanel.EXTENSIONS case in ProjectShellScreen routing on the section composable, not on PackageManagerPane internals, so the tab's content can be swapped without touching the router.

## Boundary

Explorer owns trash mechanics (EX01/EX02); Terminal owns execOnce semantics (TP03) and AgentApiServer (TP02) — this group only records the Extensions tab as a TP03-family caller and the McpPanel as TP02's UI; LSP owns the language-server session protocol (LS group) while THIS group owns the install bootstrap's invisibility (XG07); Chat owns FlowGate semantics that recommendation #2 reuses; the Performance group receives XG11/XG14 as inputs. VS Code's extension host was previously ruled "do not build" (FINAL-REVIEW §5) — this group's recommendation CONFIRMS that ruling for the host process while proposing the manifest-registry alternative the owner may consider; no gap here is fix authorization, and XC01-XC36 are pending device work on disposable rootfs/projects only.
